## 1. ActivityPrototypePage / AppWorkspaceShell route — traced call graph

- **Mount:** `AppWorkspaceShell.tsx:78` — `{activeView === 'activity' ? <ActivityPrototypePage /> : null}` inside `ActivePage`, lazy-imported at `AppWorkspaceShell.tsx:21`. Wrapped by the per-page `RecoverableRenderErrorBoundary` (`boundaryId="page.activity"`, `AppWorkspaceShell.tsx:208-221`).
- **Titlebar variant:** `TitlebarMainStrip.tsx:49` swaps the tab strip for `<ActivityTitlebarControls />` when `layout.activeView === 'activity'`.
- **Chrome layout:** `use-app-chrome-layout.ts:77` excludes `'activity'` (with `'settings'`/`'space'`) from whatever predicate that line gates — full-page surfaces suppress the normal titlebar chrome.
- **Sidebar suppression:** `WorktreeList.tsx:287` nulls `currentSidebarWorktreeId` when `activeView === 'tasks' || activeView === 'activity'`.
- **Hydration:** `use-terminal-workspace-store-bindings.ts:69` calls `useActivityTerminalPortals(activeView === 'activity')` (hook defined in `activity-terminal-portal.ts:80-90`). This is a `useSyncExternalStore` over **module-scope** state (`currentTargets`, `activity-terminal-portal.ts:16`): when `enabled` (i.e. `activeView === 'activity'`) the hook subscribes and returns live `currentTargets`; when disabled it unsubscribes and returns a shared `emptyTargets` sentinel, but does **not** clear the module-scope `currentTargets` itself — the next `setActivityTerminalPortals` call (guarded by a per-field equality check, `activity-terminal-portal.ts:29-51`) is the only thing that mutates it. Publishing an activity page → Terminal target crossing is intentionally decoupled from the app store to avoid a "wrong terminal flash" race (comment at `activity-terminal-portal.ts:56-59`).
- **Open action:** `ui-slice-view-actions.ts:6-12` — `openActivityPage()` sets `activeView: 'activity'` and stashes `previousViewBeforeActivity` (skipped if already on `'activity'`). **No `recordViewVisit`/`recordFeatureInteraction` call** — every sibling opener (`openAutomationsPage`, `openSpacePage`, `openSkillsPage`, `openArtifactsPage`, `openBotsPage`, `openMeetingsPage`) records a visit or feature interaction; `openActivityPage` is the one exception in that file (`ui-slice-view-actions.ts:1-134`, contrast lines 22-23, 37-38, 49-50, 82-83, 105-106, 118-119 against 6-12).
- **Close action:** `ui-slice-view-actions.ts:13-16` — `closeActivityPage()` restores `activeView: previousViewBeforeActivity`. Unlike `closeAutomationsPage`/`closeSkillsPage`/`closeArtifactsPage`/`closeBotsPage`/`closeMeetingsPage` (each also sets `worktreeNavHistoryIndex: rewindHistoryIndexPastView(state, <view>)`), `closeActivityPage` does **not** rewind `worktreeNavHistoryIndex`. Wired to the UI at exactly one call site: `ActivityTitlebarControls.tsx:12,29` (`onClick={closeActivityPage}`, `aria-label` "Close agents").
- **Reachability of `openActivityPage` — dead in current source.** A repo-wide, non-test grep for `openActivityPage` under `src/renderer/src` returns exactly three non-test files: `ui-slice-contract-core.ts` (type decl), `ui-slice-view-actions.ts` (implementation), and `ActivityTitlebarControls.tsx` (which only reads `closeActivityPage`, never `openActivityPage`). No component in the traced source calls `openActivityPage()`. `SidebarHeader.tsx` — the component that owns the "View activity"/"Turn off activity view" label and the `Bell` icon button most likely to be mistaken for this entry point — calls `setSidebarBody?.(agentsViewActive ? 'workspaces' : 'agents')` (`SidebarHeader.tsx:78`), a **different** state (`sidebarBody`, sidebar-panel body) than `activeView`/`openActivityPage`. `SidebarNav.tsx` (source) has zero references to `openActivityPage` or the string `Activity`, even though `SidebarNav.test.tsx:18,133` mocks and injects an `openActivityPage` prop — the mock is now exercising a prop the current component does not read. The only other reference to `activeView === 'activity'` transitions is `automation-dispatch-handler.ts:221`, which calls the generic `setActiveView(focusBeforeDispatch.activeView)` to restore whatever view was focused before a dispatch (including `'activity'` if that was already the active view) — this is a restore path, not a fresh open trigger, and does not set `previousViewBeforeActivity`.
- **Net finding:** `ActivityPrototypePage` renders correctly if `activeView` is externally forced to `'activity'` (store test, automation-restore replay, or a future caller), and it has one wired, reachable close path — but no wired, reachable **open** path exists in the current renderer source tree. This is consistent with, and sharpens, the parent report's note that ActivityPrototypePage "needs explicit ownership/reachability characterization" (`report.md:17`).
- **Naming collision (real, not cosmetic):** two independent boolean-ish states are both called "activity"/"agents" in user-facing strings: (a) `activeView === 'activity'` → full-page `ActivityPrototypePage`, titlebar label "Close agents"; (b) `sidebarBody === 'agents'` → sidebar-panel body swap in `SidebarHeader.tsx`, tooltip label "View activity" / "Turn off activity view". `ui-page-navigation.test.ts:301-311` ("returns to the graduated Agents view after visiting settings") tests (a) via `openActivityPage()`/`activeView`, confirming the source's own test vocabulary calls the full-page surface the "Agents view," the same name the sidebar tooltip uses for the unrelated (b) state. Any central navigation ID scheme must key these separately (see §3) to avoid silently merging two different surfaces under one id.

## 3. Settings-navigation types/foundations and deep links — proposed collision-free central IDs

Source of truth: `settings-navigation-types.ts:15-51` (`SETTINGS_NAV_TARGETS`, exactly **35** literal pane ids, verified by direct count), `:53-57` (`SETTINGS_NAV_INTENTS`, 3 named intents), `:65-71` (`SettingsNavigationTarget` shape: `{ pane, repoId, hostId?, sectionId?, intent? }` — `repoId` is the dynamic-per-repo axis, orthogonal to `pane`), `settings-navigation-foundations.ts:10-45` (8 named groups: `capabilities`, `setup`, `workflows`, `interface`, `remote`, `security`, `advanced`, `experimental`).

The existing `PUI-SETTINGS-001..035` range notation collides with the already-assigned `PUI-SETTINGS-002` (search) and `PUI-SETTINGS-003` (deep-link watcher) ids — a naive `001`-indexed pane list would produce two different things named `PUI-SETTINGS-002`/`003`. This leaf proposes a **pane-qualified** id family that never reuses a bare number, so it cannot collide with `000`/`002`/`003` regardless of ordering, and folds the dynamic `repo` pane and the 3 intents into the same scheme instead of inventing a second denominator:

- **Fixed panes (35):** `PUI-SETTINGS-PANE-<pane-id>`, where `<pane-id>` is the literal string from `SETTINGS_NAV_TARGETS` (e.g. `PUI-SETTINGS-PANE-general`, `PUI-SETTINGS-PANE-integrations`, … `PUI-SETTINGS-PANE-mobile-emulator`, `PUI-SETTINGS-PANE-repo`). Using the source string itself as the suffix (not a re-assigned ordinal) means the id is stable across any future reordering of the tuple and self-documents which pane it names.
- **Dynamic per-repo pane:** `PUI-SETTINGS-PANE-repo` (already covered above, since `'repo'` is a literal member of `SETTINGS_NAV_TARGETS`) qualified per-instance as `PUI-SETTINGS-PANE-repo:<repoId>` only where a specific repo instance's rendered state must be distinguished (e.g. a screenshot state) — the bare `PUI-SETTINGS-PANE-repo` id covers the pane's shared behavior/type contract.
- **Named intents (3):** `PUI-SETTINGS-INTENT-<intent-id>` → `PUI-SETTINGS-INTENT-add-quick-command`, `PUI-SETTINGS-INTENT-add-remote-orca-server`, `PUI-SETTINGS-INTENT-add-ssh-host`, sourced from `SETTINGS_NAV_INTENTS` (`settings-navigation-types.ts:53-57`).
- **Named sub-targets already assigned constants** (not part of the 35+3, but in the same file and liable to the same collision risk): `FULL_DISK_ACCESS_SETTINGS_TARGET_ID`, `BROWSER_TERMINAL_LINK_ACTIONS_SETTINGS_TARGET_ID`, `BROWSER_CLIENT_HOSTED_REMOTE_SETTINGS_TARGET_ID`, `BROWSER_SSH_WORKSPACE_ROUTING_SETTINGS_TARGET_ID`, `GLOBAL_WORKTREE_VISIBILITY_SETTINGS_TARGET_ID` (`settings-navigation-types.ts:61-64`) → propose `PUI-SETTINGS-SUBTARGET-<constant-value>` (e.g. `PUI-SETTINGS-SUBTARGET-developer-permissions-full-disk-access`) to keep them in the same collision-free family rather than letting them float unassigned.
- **Groups (8):** not separately numbered by the source obligation, but if the E1 lead wants group-level ids for coverage bookkeeping: `PUI-SETTINGS-GROUP-<group-id>` (`capabilities`/`setup`/`workflows`/`interface`/`remote`/`security`/`advanced`/`experimental`).

**Preserved exactly as-is, no renumbering proposed:**
- `PUI-SETTINGS-000` — aggregate/taxonomy card (`parity-ui-capability-cards.json:94-118`), whose `screenshotStatesNeeded` (`SHOT-SET-<pane>-01 (x35, …)`, line 109) should be read as one shot per `PUI-SETTINGS-PANE-<pane>` under this scheme.
- `PUI-SETTINGS-002` — search (`parity-ui-capability-cards.json:126+`).
- `PUI-SETTINGS-003` — deep-link target watcher (`report.md:233`; source `settings-deep-link-target-watcher.ts`, traced in §2 above).
- `PUI-SETTINGS-001` is **retired from standalone-card use** per this leaf's proposal (it was always the ambiguous "001..035" range head, per `report.md:232` and `closure.json:4995`); its obligations fold into `PUI-SETTINGS-000` plus the per-pane `PUI-SETTINGS-PANE-*` ids above. This leaf does not delete or renumber the existing `PUI-SETTINGS-001` closure.json entry — that edit belongs to the E1 lead, who owns `report.md`/`closure.json`.

This scheme is collision-free by construction: `PANE-`, `INTENT-`, `SUBTARGET-`, and `GROUP-` prefixes partition the id space so no fixed pane, dynamic repo instance, named intent, or sub-target constant can ever produce the same id as another, or as `000`/`002`/`003`.
