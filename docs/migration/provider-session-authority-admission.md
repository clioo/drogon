`crates/drogon-core/src/session_authority/` — record/lease/handle/link/process
validators, typed deserialization, persisted-record admission with

## Correction: schemaVersion numeric equivalence (the one real mismatch)

Pre-fix RED (bounded evidence in
`tests/parity/ports/WP-ENG-RUNTIME/native-session-authority/provider-record/red-round-matrix.txt`):
exactly **one** of 266 cases disagreed — `record:schemaVersion:2.0`, which the
pinned source admits (JavaScript `record.schemaVersion === 2` compares
doubles, so `2`, `2.0`, `2e0` and any decimal spelling equal to 2 are the
supported version) but the candidate rejected, in the validator
(`Value::Number` integer equality), in admission (`Number::as_u64` gate), and
therefore in the typed roundtrip. The other 265 cases already agreed.

Fix: both `is_agent_session_record` and `admit_persisted_record` now compare
`schemaVersion` through `is_supported_schema_version`, an `as_f64() == 2.0`
JavaScript-number-equality check. Nothing else changed semantically:

- Unknown-version quarantine preserved: any present version that is not
  number-equal to 2 → `RecordReadError::UnsupportedSchema` with the raw value
  never rewritten; an object with no `schemaVersion` key → `Invalid`.
- `minimumNextFence` stays deliberately unvalidated by the lease validator
  and is preserved verbatim (null, absent, fraction, string, object, array)
  through admission and typed re-serialization — asserted by dedicated tests.
- Null-versus-absent field rules and the shared `js_trim` /
  `json_safe_integer` policy are unchanged.
- Typed deserialization keeps using the same `json_safe_integer` extraction
  as the validators, so `2.0`/`1e0`/`-0` spellings land on identical
  decisions in validation, admission, and typed roundtrip.
